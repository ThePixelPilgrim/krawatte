# Roadmap: restart, Krawattefile, watching, control CLI

Decisions taken on 2026-08-20 that bind the next four specs. Each item below
gets its own spec and implementation plan; this file exists so later specs do
not reopen what is settled here.

## Motivation

Today a dev cluster looks like

```
krawatte "watchexec -r -w server/src -- cargo run -p server" "npm run dev"
```

watchexec puts its child in its own process group, outside the group krawatte
signals, so the child can outlive krawatte when watchexec is slow to forward
the signal. Owning restart-on-change inside krawatte removes that middleman:
every process is in a group krawatte created and can always reach.

Beyond that, a coding agent working alongside the TUI needs to restart slots
and read their output without a terminal, and a project should be launchable
with a bare `krawatte` in its directory.

## Build order

| # | Spec | What it delivers |
|---|---|---|
| A | restart core | per-slot kill→respawn in place, `r`/`k` hotkeys, generations, one-shot override model |
| B | Krawattefile | named slots with `cmd`, `cwd`, `env`, `watch`; bare `krawatte` launches it |
| D | file watching | `watch` paths (including `"self"`) trigger the restart primitive; retires watchexec |
| C | control socket + CLI | `krawatte restart/status/logs/run …` against a running TUI |

D precedes C because retiring watchexec is the original pain and the
override trigger in C is only plumbing once A models it.

## Settled decisions

**Restart primitive.** The manager's one core operation is "replace this
slot's generation with command X; on its exit do Y", Y ∈ {stay dead, spawn the
standard command}. `r`, watch-triggered restart, and the override are three
callers of that primitive. See the restart-core spec.

**Hotkeys.** `r` restarts the slot's *current* generation (standard or
override) with the same command. `k` kills the current generation and lets the
on-exit policy run: in an override the standard run resumes; in the standard
run it behaves like `r`. Both are silent no-ops in the all-view and while a
restart is already in flight. A standard run that exits on its own stays dead
— there is no crash-restart.

**Two-stage cargo setup.** `cargo run` is a poor restart unit (compile and
serve in one process). The intended Krawattefile shape is two slots linked only
through the filesystem:

```toml
[[proc]]
name  = "build"
cmd   = "cargo build -p erhebimus"
watch = ["platform/server/src", "platform/server/migrations"]

[[proc]]
name  = "server"
cmd   = "target/debug/erhebimus"
watch = "self"          # the path of the command's first token
```

Watch semantics are uniform: on change → if running, TERM→grace→KILL; then
(re)spawn. The build slot is normally dead between changes and its exit code
is the compile result; a failed build leaves the old server running because
the binary did not change. Cargo renames the binary into place, so `"self"`
watches the parent directory filtered by name, and the file is always complete
when observed. A short debounce coalesces bursts.

**Override is pinned.** While a one-shot override (e.g. `perf record -g …`)
runs, watch events for that slot are ignored. It ends when it exits on its
own, or via `k`; `r` restarts the override itself.

**Log storage.** The existing per-slot ring buffer (~10,000 lines, ANSI kept,
arrival time per line) is the only store. The CLI `logs` command reads it over
the socket; no new storage, no persistence. ANSI is stripped by default in CLI
output, kept with `--color`. Restart keeps the buffer and inserts a block of
marker lines (generation numbers, pids, old outcome and runtime, command,
later the trigger) rather than clearing it; one topic per line rather than
one overlong line.

**Entry points.** One binary, three modes: positional command strings → ad-hoc
cluster (unchanged); no arguments + Krawattefile in cwd → launch it;
subcommand → control a running instance. The socket path derives from the
Krawattefile's directory so an agent in the same cwd needs no configuration.

**Out of scope.** Headless/daemon mode (`krawatte up -d`, attach, log
persistence): the TUI is the server. If none is running, the CLI fails with
"no krawatte running in this directory". Crash-restart policies, dependency
ordering between slots, and gitignore-aware filtering beyond a simple
exclude list are likewise deferred until a concrete need appears.
